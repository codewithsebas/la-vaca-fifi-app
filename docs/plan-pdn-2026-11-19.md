## Por qué en este orden

La versión actual de `main` funciona con las dos migraciones aplicadas: `is_admin()` sigue aceptando `admin` y los
disparadores solo agregan filas a una tabla que esa versión no usa. La versión nueva, en cambio, lee `activity_log` y registra
los inicios de sesión allí. Por eso **las migraciones van antes que el código.**

## Riesgos

1. **Primer ingreso guiado para todos.** Ninguna cuenta de PDN tiene `tour_done`: la próxima vez que cada persona del equipo
   entre, el panel le pedirá nombre y foto antes de seguir, y le mostrará el recorrido. Avisar al equipo.
2. **Colores del sitio guardados.** Desde el 9 de noviembre el sitio ignora `site_settings.theme`; la versión nueva lo vuelve a
   aplicar si es distinto de la paleta de la marca. Si en PDN quedaron colores viejos, la portada cambiará de color. El paso 0
   lo revisa; si hay colores viejos, se decide antes si se dejan o se vacía `theme` (con el valor anotado para volver atrás).
3. **Disparadores en tablas con tráfico real.** Cada escritura del equipo hace una inserción más. Es una fila pequeña por
   cambio; en QA no se notó.
4. **Next 16.4.6 en Hostinger.** QA ya compiló y publicó con esta versión el 19 de noviembre, pero ese despliegue no arrancó
   solo: hubo que redesplegar a mano desde el panel de Hostinger. Puede pasar lo mismo en PDN.

## Si algo sale mal

| Falla en         | Qué hacer                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| Paso 2           | Cada migración es una transacción: si falla, se deshace sola. Se revisa el error antes de reintentar.        |
| Paso 3 (compila) | Hostinger deja la versión anterior; nada cambió. Se revisa el registro de compilación.                       |
| Paso 4           | Revertir el merge en `main` y push. Las migraciones pueden quedarse: la versión anterior funciona con ellas. |
| Quitar migración | Solo si hace falta, con el SQL de abajo, en una transacción. Borra el registro de actividad acumulado.       |

```sql
-- Deshacer 20261119010000 (registro de actividad)
do $$ declare t text; begin
  for t in select tgrelid::regclass::text || '|' || tgname from pg_trigger where tgname like '%\_activity' and not tgisinternal loop
    execute format('drop trigger %I on %s', split_part(t, '|', 2), split_part(t, '|', 1));
  end loop;
end $$;
drop function public.log_activity_change();
drop function public.activity_diff(jsonb, jsonb);
drop function public.activity_value(text, jsonb);
drop table public.activity_log;
delete from supabase_migrations.schema_migrations where version = '20261119010000';

-- Deshacer 20261119000000 (superadministrador): primero quitar el rol a cualquier cuenta superadmin.
create or replace function public.is_staff() returns boolean language sql stable set search_path = ''
  as $$ select public.panel_role() in ('admin', 'recepcion') $$;
create or replace function public.is_admin() returns boolean language sql stable set search_path = ''
  as $$ select public.panel_role() = 'admin' $$;
drop function public.is_superadmin();
delete from supabase_migrations.schema_migrations where version = '20261119000000';
-- Las políticas reescritas a is_admin() se dejan así: con is_admin() restaurado equivalen a las de antes.
```

Antes de usar este SQL se compara la definición original de `is_staff` e `is_admin` en el respaldo del paso 1.
